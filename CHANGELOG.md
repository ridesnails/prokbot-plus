# 更新记录 / Changelog

版本号从 ProkBot Plus 1.0.0 开始。上游 ProkBot 的版本记录附在后面，供参考。

Versions start at ProkBot Plus 1.0.0. Upstream ProkBot releases are listed at the end for reference.

## ProkBot Plus 1.5.1 (2026-11-19)

修复上游 ProkBot 作者在合并评审（[Gitee PR #2](https://gitee.com/ahaduoduoduo/ProkBot/pulls/2)）中指出的问题。服务端的修复要升级 Host 才生效；桌面客户端的修复要重新生成 Windows（或 Mac）客户端。Android、网页版和 iOS 客户端与 1.5.0 相同。

Fixes for problems the upstream ProkBot author found while reviewing the merge ([Gitee PR #2](https://gitee.com/ahaduoduoduo/ProkBot/pulls/2)). Upgrade the Host for the server fixes and rebuild the Windows (or Mac) client for the desktop fixes. The Android, web and iOS clients are the same as in 1.5.0.

- **OpenAI Chat 兼容接口 / OpenAI Chat-compatible endpoints**：OpenAI Chat 一直比上游严格：必须同时收到 `[DONE]` 和 `finish_reason`，`finish_reason` 是 `stop` 却带了工具调用、或是不认识的结束原因，整轮对话都会报错；工具参数是空字符串也会报错。有些兼容接口正是这样返回的。现在照上游原来的方式处理：两个结束标记有一个就行，`stop` 带工具调用时照常执行工具，空参数在工具没有必填参数时按 `{}` 处理（OpenAI Responses 接口也一样），有必填参数时仍然报错，免得丢了参数的调用被当成空参数执行。被截断、两个标记都没有的回复仍会被拒绝。OpenAI Chat has been stricter than upstream: it required both `[DONE]` and `finish_reason`, failed the whole turn on `stop` with tool calls or on an unknown finish reason, and rejected an empty argument string, all of which some compatible endpoints send. It now follows upstream's original handling: either end marker completes the stream, tool calls run after `stop`, and an empty argument string means `{}` for a tool with no required parameters (OpenAI Responses too). A tool with required parameters still rejects it, so a call whose arguments were lost is never run with none. A truncated reply with neither marker is still rejected.
- **桌面客户端遇到 401 / Desktop client and HTTP 401**：Mac 和 Windows 客户端收到任何 401 都会断开连接、要求重新配对；连接器的 OAuth 授权过期又没有刷新令牌时 Host 也返回 401，用户只能重新配对或重启。现在先用 `/connect/status` 核对设备凭据，只有设备确实失效才断开；否则只让这次请求失败。没有这个接口的旧 Host 照上游原来的方式弹出配对窗口，不断开连接。Any 401 made the Mac and Windows clients disconnect and ask to pair again, and the Host also answers 401 when a connector's OAuth grant expires without a refresh token. The client now checks the device credential with `/connect/status` and disconnects only when the device itself is rejected; otherwise only that request fails. An older Host without that endpoint gets upstream's original pairing prompt without disconnecting.
- **桌面设置文件损坏 / Damaged desktop profile**：`local-client-persistence.json` 解析失败后，之后每次读写都失败，账号和侧边栏状态都恢复不了；旧版本不是原子写入，升级的用户可能已经带着损坏的文件。现在把它改名为 `local-client-persistence.json.damaged-<时间>` 保留，再按空数据继续，账号和侧边栏状态从 Host 重新读取。读不了文件（例如权限问题）时仍然报错并保留原文件。When `local-client-persistence.json` could not be parsed, every later read and write failed, and earlier clients did not write it atomically. The damaged file is now kept as `local-client-persistence.json.damaged-<time>` and the client continues with empty data, reading the account and sidebar state from the Host again. A file that cannot be read at all (a permission problem, for example) is still reported and preserved.
- **启动闪白 / Startup flash**：系统是浅色模式时，桌面客户端窗口先显示白色底，等设置加载后才变回深色；现在一开始就按保存的主题（默认深色）显示。With a light system theme, the desktop window started white and turned dark only after the settings loaded; it now starts with the saved theme (dark by default).
- **消息顺序 / Message order**：有的服务按序号生成工具调用 ID，两个对话同时回复时可能用到同一个 ID，后一个对话会直接报错；现在这条消息不参与排序（一分钟后恢复），两个对话都照常进行。Some services number tool call IDs, so two conversations replying at once could reuse an ID and the second failed. That message now runs unordered (for one minute) and both conversations continue.
- **其他 / Other**：Codex 的系统提示不再对所有用户写「Mac 或 Windows PC」，改成「已连接的电脑」；`deploy.py recover` 拒绝没有镜像 ID 的旧备份时，错误信息直接给出只恢复数据的命令；iOS 的 `patch-app.py` 从 `recipes/ios/manifest.json` 读取支持的版本，不再写死 1.16.0。The Codex system prompt now says "a connected computer" instead of "a Mac or Windows PC" for every user; when `deploy.py recover` refuses a backup without recorded image IDs, the message gives the exact data-only restore command; iOS `patch-app.py` reads the supported version from `recipes/ios/manifest.json` instead of hard-coding 1.16.0.
- **官方版本记录 / Official release record**：官方 Windows 和 Mac 客户端已更新到 1.2.3，iOS 商店是 1.26.0（2026-11-19 核对）。首页版本表、徽章、技术文档和交接文档已更新；本项目尚未适配 1.2.3，补丁仍只接受 1.1.0 和 0.71.2，Windows 说明提醒不要用官方网站上的最新安装包。The official Windows and Mac clients are now at 1.2.3 and the iOS store at 1.26.0 (checked November 19, 2026). The homepage version table and badges, the architecture notes and the handoff are updated. This project does not support 1.2.3 yet; the patches still accept only 1.1.0 and 0.71.2, and the Windows README warns against the latest installer on the official site.
- **问题模板 / Issue templates**：问题报告加入「网页版」选项，并引导功能请求改用功能建议模板；功能建议模板增加「相关部分」。The bug report form gains a web client option and points feature requests to their own form, which now asks for the related part.
- **验证 / Validation**：以上每项都有回归测试，各套测试的通过数见交接文档。这一版没有在真实服务器或 Mac 上验收；Android 和网页版自己的连接层对 401 仍是原来的处理，没有改。Each fix has regression tests; pass counts are in the handoff. This release was not checked on a real server or a Mac. The Android and web clients' own connection layer still handles 401 as before.

## ProkBot Plus 1.5.0 (2026-11-19)

新增网页版：在 Windows、Mac、Linux 电脑，Android 和 iPhone 手机，iPad 和安卓平板的浏览器里使用自己 Host 上的 Bot，不用安装客户端，排版随屏幕自适应。要升级 Host 才能用。Windows、Mac、iOS 客户端与 1.4.0 相同；Android 客户端随之修了一个问题（点击通知冷启动时偶尔打不开对应的 Bot），重新生成 APK 后生效，不重新生成也能照常使用。

New web client: use the Bots on your own Host from a browser on Windows, Mac or Linux computers, Android phones, iPhones, iPads and Android tablets, with no client to install and a layout that adapts to the screen. Upgrade the Host to use it. The Windows, Mac and iOS clients are the same as in 1.4.0. The Android client gets one fix shared with the web client (a cold start from a notification could miss the target Bot); it takes effect after rebuilding the APK, and the existing APK keeps working.

- **网页版 / Web client**：在电脑上运行 `node web/patchers/patch.mjs`，从自己下载的官方 Windows 安装包（推荐 1.1.0，可回退 0.71.2）生成界面包，在管理页新的「网页版」页上传，或加 `--upload <Host 地址>` 直接装到 Host。之后在任何设备的浏览器打开 `Host 地址/web/`，输入「设备与通知」里创建的配对码登录；管理页所在的浏览器可以直接点「在此浏览器打开」。界面和 Android 客户端相同：电脑和横屏平板是官方桌面版排版，竖屏平板收起侧栏，手机照官方手机版排版；浏览器的返回键和返回手势逐级返回；手机键盘不会挡住输入框；可以添加到主屏幕全屏打开。Bot 的电脑可以实时查看和操作，附件可以上传、下载，页面开着时没在看的 Bot 有新消息会弹出浏览器通知。网页版只使用 Host 上的 Bot 电脑，不能操作浏览器所在的设备，不支持 Tailcat；http 地址下麦克风、语音输入和通知不可用。说明见 [`web/README.md`](web/README.md)。On a computer, run `node web/patchers/patch.mjs` to build an interface bundle from the official Windows installer you download yourself (1.1.0 recommended, 0.71.2 as fallback), then upload it on the admin page's new **Web client** page, or add `--upload <Host address>` to install it directly. Then open `<Host address>/web/` in any device's browser and sign in with a pairing code created under **Devices & notifications**; the browser with the admin page can click **Open in this browser** instead. The interface is the same as the Android client's: the official desktop layout on computers and landscape tablets, a folded sidebar on portrait tablets and the official phone layout on phones. The browser's back button and gesture go back one step at a time, the phone keyboard does not cover the message field, and the page can be added to the home screen to open full screen. The Bot's computer can be watched and operated live, attachments upload and download, and while the page is open, new messages from Bots not on screen raise browser notifications. The web client uses only the Bot's computer on the Host, cannot operate the device the browser runs on and does not support Tailcat; on an http address the microphone, dictation and notifications are unavailable. See [`web/README.en.md`](web/README.en.md).

- **安全 / Security**：界面包含有官方界面，只保存在用户自己的 Host 上，项目不分发。Host 按包内清单核对每个文件的大小和 SHA-256 后整体换入，失败时保留原包；未登录的访问者只能看到 Host 自己的登录页。登录凭据是 HttpOnly、SameSite=Strict 的 Cookie，调用设备接口还要带专用请求头并来自 Host 自己的地址；每个浏览器是一台 `web` 设备，可以在「设备与通知」里撤销，没有桌面执行权限。The bundle contains the official interface; it stays on the user's own Host and the project does not distribute it. The Host checks the size and SHA-256 of every file against the bundle's manifest and swaps the bundle in as a whole, keeping the previous one if anything fails; visitors who have not signed in see only the Host's own sign-in page. The sign-in credential is an HttpOnly, SameSite=Strict cookie, and device API calls must also carry a dedicated header and come from the Host's own address. Each browser is a `web` device that can be revoked under **Devices & notifications** and has no desktop execution permission.

- **共用桥接的修复 / Shared bridge fixes**：Safari（iPhone、iPad、Mac）的 ResizeObserver 不支持 `device-pixel-content-box`，网页版打开带图片的对话时整个对话变白；`compat.js` 在缺少该能力时改用 `content-box`，Android WebView 已支持该能力，不受影响。点击通知或链接冷启动时，打开 Bot 的指令可能早于 Bot 列表到达而被丢掉，Android 和网页版都有这个问题；现在先确认 Bot 存在、等列表出现后再打开。Safari's ResizeObserver (iPhone, iPad, Mac) does not support `device-pixel-content-box`, so opening a conversation with an image in the web client blanked it; `compat.js` observes `content-box` instead where the feature is missing, and Android WebView, which has the feature, is unaffected. On a cold start from a notification or link, the request to open a Bot could arrive before the Bot list and be lost, on Android and in the web client alike; the bridge now confirms the Bot exists and waits for the list before opening it.

- **发布包 / Release packages**：Release 增加第六个工具包 `prokbot-plus-web.zip`（含 `web/`、`android/`、`windows/`、`mac/`）。首页的版本徽章和客户端表格加入网页版。Releases gain a sixth tool archive, `prokbot-plus-web.zip` (with `web/`, `android/`, `windows/` and `mac/`). The homepage version badges and client table list the web client.

- **验证 / Validation**：Playwright 用 Chromium、Firefox、WebKit 三种浏览器内核，在 Windows 电脑、Mac 电脑、Android 手机和平板、iPhone 15、iPhone SE、横屏 iPad Pro 11 共 8 种设备尺寸上，对 1.1.0 和 0.71.2 两种界面各跑一遍完整流程（配对登录、链接打开对话、看图、通知、发消息、手机返回、刷新后保持登录，Windows Chrome 另测退出登录和从管理页打开），全部通过。另在一台真实 Linux 服务器的隔离测试实例上，验证了命令行和管理页上传、局域网 http 登录、真实模型对话、Bot 操作自己的电脑并发回截图，以及电脑和 iPhone 尺寸下的电脑实时画面；测试实例和镜像已全部清理，生产 Host 未改动。没有在 iPhone、iPad、Android 真机的浏览器上测试。各套测试的通过数见交接文档。Playwright ran the full flow (pairing, opening a conversation from a link, images, notifications, sending, phone back navigation, staying signed in after a reload, plus sign-out and opening from the admin page on Windows Chrome) on Chromium, Firefox and WebKit at 8 device sizes (Windows computer, Mac computer, Android phone and tablet, iPhone 15, iPhone SE, landscape iPad Pro 11) for both the 1.1.0 and 0.71.2 interfaces; all passed. An isolated test instance on a real Linux server also verified uploading from the command line and the admin page, LAN http sign-in, a real model conversation, a Bot operating its own computer and sending back a screenshot, and the live computer view at desktop and iPhone sizes; the instance and its images were removed afterwards and the production Host was not touched. Browsers on physical iPhones, iPads and Android devices were not tested. Test counts are in the handoff document.

## ProkBot Plus 1.4.0 (2026-11-18)

Host 新功能（社区贡献，[PR #2](https://github.com/ferretgeek/prokbot-plus/pull/2)，作者 @jun9100）：可以给每个 Bot 单独选模型并配备用模型，主模型出错时自动换备用；可以手动压缩 Bot 的上下文。要升级 Host 才能用；客户端与 1.3.0 相同，不用重新生成。

New Host features (community contribution, [PR #2](https://github.com/ferretgeek/prokbot-plus/pull/2) by @jun9100): each Bot can have its own model with backups that take over when the primary fails, and a Bot's context can be compacted on demand. Upgrade the Host to use them; the clients are the same as in 1.3.0 and need no rebuild.

- **按 Bot 路由与上下文压缩 / Per-Bot routing and compaction**：新的模型页以“服务 → 档案 → 默认路由 → Bot 路由”配置模型。一个服务可有多个档案，默认路由用于未覆盖的 Bot，单个 Bot 可指定主档案、思考强度和最多 8 个有序备用档案；直接路由不调用 Jev，子代理继承父 Bot 的路由。档案可手动设置上下文容量和摘要阈值，服务商目录返回容量时会带入参考阈值；阈值为 0 时沿用 Harness 策略。新档案不再默认 258K / 192K。Bot 路由页可在 Bot 空闲时手动压缩上下文，成功的模型响应也会把配置阈值报告给 Harness，用于阈值触发的自动压缩。旧的按任务难度/Jev 配置继续运行；首次从新页面保存前会明确要求确认迁移，取消或未确认不会改写旧配置。只配了一个模型的旧配置不涉及 Jev，页面只说明保存时会转成新格式，模型、API Key 和思考强度不变。**行为变化**：旧配置若已经同时设置非零上下文容量和摘要阈值，升级后会真正启用按阈值自动压缩。**Per-Bot routing and compaction**: the model page now separates services, profiles, a default route and Bot routes. One service can have multiple profiles, the default route covers Bots without an override, and each Bot can name a primary profile, thinking effort and up to eight ordered backups. This direct route does not call Jev, and subagents inherit their parent Bot's route. Profiles can set context capacity and summary thresholds explicitly; provider catalog capacity supplies a recommended threshold, while zero keeps the Harness policy. New profiles no longer start at 258K / 192K. The Bot route list can summarize an idle Bot on demand, and a successful model response reports configured thresholds to the Harness for threshold-triggered compaction. Existing task-difficulty/Jev configuration keeps running until an administrator confirms migration from the new page; cancelling or omitting confirmation leaves the old configuration untouched. A legacy single-model configuration never used Jev, so the page only notes that saving converts it to the new format with the same model, API key and thinking effort. **Behavior change**: a legacy configuration that already had non-zero context and summary thresholds will begin automatic compaction at that threshold after upgrade.

- **主/备模型与流式可靠性 / Primary-backup routing and stream reliability**: 主模型尚未输出可见文字或工具调用时，402、408、429、5xx、网络错误或上游 HTTP/SSE I/O 空闲超时可按顺序尝试备用档案；Host 的 I/O 空闲默认 300 秒，Harness 自己的 150 秒首字停滞截止时间通常会先结束首字停滞。输出后不切换，避免重复回复和工具副作用。只有明确额度耗尽会跳过共用 API Key 的备用档案；普通 503、超时和网络错误仍可尝试同一 Key 下的另一个模型。备用模型接管后，本轮后续步骤继续优先使用它，下一轮重新从主模型开始。调用方取消或超时不会触发备用请求，响应体在提前结束和失败切换时都会关闭。SSE 解析不再在每个分块到达时从头扫描大型事件（单个 15 MB 事件约 1.7 秒，仍慢于逐行解析），失败尝试的用量和请求 ID 各自归因。Anthropic 签名思考按服务商和接口格式隔离，但不再因日期快照或中转改写模型名而丢弃回放。**Primary-backup routing and stream reliability**: while no visible text or tool call has escaped, 402, 408, 429, 5xx, network errors and upstream HTTP/SSE I/O idle timeouts can try backup profiles in order; the Host I/O idle deadline defaults to 300 seconds, while the Harness's own 150-second first-token stall deadline usually ends a first-token stall first. There is no switch after output, avoiding duplicate replies and tool side effects. Only explicit quota exhaustion skips a backup that shares the API key; ordinary 503, timeout and network failures can still try another model under the same key. After a backup takes over, the rest of that turn keeps preferring it; the next turn starts from the primary again. Caller cancellation or timeout does not start a backup request, and response bodies close on early exit or failure switching. SSE parsing no longer rescans a large event from its start on every chunk (a single 15 MB event takes about 1.7 seconds, still slower than line-based parsing), and failed attempts keep their own usage and request IDs. Anthropic signed thinking remains isolated by provider and API format without discarding replay merely because a dated snapshot or gateway rewrote the model ID.

- **模型管理安全与界面 / Model administration safety and UI**: 服务商、档案和 Bot 名称不再作为 SVG/HTML 写入图标位置，仅接受内置图标。英文界面补齐刷新 Bot、默认服务、模型迁移和回退记录文字。Provider, profile and Bot names are no longer treated as SVG/HTML in icon slots; only built-in icons are accepted. English translations now cover refreshing Bots, the default service, routing migration and fallback records.

- **验证 / Validation**: Host 回归测试覆盖持续输出、上游停滞、消费者背压、取消、同一/独立 Key 的备用、Anthropic 别名思考、工具循环接管、失败用量、SSE 大事件、旧 Jev 配置保护、从 Host 入口到 HTTP 请求的 Bot 路由、完整 recipe 应用和手动压缩。管理页浏览器测试覆盖两种旧配置的迁移提示。四套项目测试的通过数见交接文档。另在 Docker 29.1.3 + Compose 2.40.3 的独立测试实例上用真实 Anthropic Messages 模型验收：从 1.3.1 升级后旧对话和旧配置照常可用；未确认迁移的保存返回 409；主模型不可达时，一轮两次工具调用只切换一次备用；空闲 Bot 手动压缩 8 秒完成，之后仍记得先前的操作，运行中的 Bot 返回 409。生产 Host 尚未升级。Host regressions cover sustained output, upstream stalls, consumer backpressure, cancellation, same-key and independent-key backups, Anthropic alias thinking, tool-loop takeover, failed-attempt usage, large SSE events, legacy Jev protection, Bot routing from the Host entry point to the HTTP request, full recipe application and manual summarization. The admin-page browser test covers the migration notice for both kinds of legacy configuration. Pass counts for the four project suites are in the handoff document. A separate test instance on Docker 29.1.3 with Compose 2.40.3 was also checked against a real Anthropic Messages model: after upgrading from 1.3.1, earlier conversations and the legacy configuration kept working; saving without confirming migration returned 409; with an unreachable primary, a turn with two tool calls switched to the backup only once; summarizing an idle Bot took 8 seconds and the Bot still remembered its earlier actions, while a running Bot returned 409. The production Host has not been upgraded yet.

## ProkBot Plus 1.3.1 (2026-11-17)

Host 部署工具修复：在 Docker 29 + Compose 2.40 上，`deploy.py backup` 和 `deploy.py update` 无法运行（[#4](https://github.com/ferretgeek/prokbot-plus/issues/4)）。另外升级了 GitHub 依赖提醒指出的几个依赖。客户端与 1.3.0 相同，不用重新生成。

Host deployment tool fix: on Docker 29 with Compose 2.40, `deploy.py backup` and `deploy.py update` could not run ([#4](https://github.com/ferretgeek/prokbot-plus/issues/4)). Several dependencies flagged by GitHub's dependency alerts were also updated. The clients are the same as in 1.3.0 and need no rebuild.

- **备份与升级 / Backup and update**：备份和升级前读取容器信息时报 `map has no entry for key "Mounts"`，在停机前中止，服务不受影响，但无法备份或升级。原因是 `docker inspect` 的模板因 `.Id` 改读原始 JSON，而原始 JSON 会省略空字段：Compose 2.40 用 Binds 挂载具名卷时没有 `HostConfig.Mounts`，不带选项的 `--mount` 没有 `VolumeOptions`。`host/release/backup.py` 现在用 `index` 读取这几个可能缺失的键，仍然只取用了子目录挂载的目标路径，用卷的子目录冒充整个数据卷的容器照样被拒绝。Reading container details before a backup or update failed with `map has no entry for key "Mounts"` and stopped before any service was stopped, so services kept running but nothing could be backed up or upgraded. `.Id` makes `docker inspect` run the template on the raw JSON, which omits empty fields: Compose 2.40 mounts named volumes as Binds, leaving no `HostConfig.Mounts`, and `--mount` without options leaves no `VolumeOptions`. `host/release/backup.py` now reads these optional keys with `index`, still projecting only the targets of subdirectory mounts; a container that mounts a volume subdirectory in place of the whole data volume is still refused.

- 备份只查询所选项目的来源。非 Host 卷和工具自己的锁不阻塞无关部署；来源不明的恢复卷不能自动上线。容量报告不再把构建窗口外的样本或聊天中未解释的进程代次变化计为通过。 Backups look up only the selected project's origin. Unrelated Compose volumes and the tool's own locks do not block deployment; restored identities of unknown origin still cannot start automatically. Capacity comparisons reject builds without an in-window sample interval and service generations inconsistent with Docker start events.

- **Windows 并行安装 / Windows side-by-side installs**：安装器保留了旧版，但新客户端首次启动仍会改写旧的开始菜单快捷方式和 `grokbot-local:` URL 关联。现在保留已占用的入口，并行安装和隔离 QA 启动均不注册这两项。The installer preserved the legacy copy, but first launch could still replace its Start menu shortcut and URL handler. Occupied entries are now preserved; side-by-side and isolated QA launches register neither.
- **分机模型状态 / Split Host model status**：仅保存模型、未启用执行节点时，管理页曾一直等待，CLI 三分钟后报错。现在概览的「配置节点」打开「执行环境」设置，CLI 明确报告模型已保存、尚未应用。With a saved model but no enabled execution node, the console used to wait indefinitely and the CLI timed out after three minutes. Overview now opens the Execution settings and the CLI reports saved, not applied.

- **部署与恢复 / Deployment and recovery**：候选先构建，拒绝漏备份的挂载，核对 Host 和桌面镜像。备份只含受管卷和清单，不含镜像、实例 `.env` 或宿主机系统；`recover` 使用目标 daemon 已有的精确镜像和新卷。跨 daemon 由操作者保证互斥及同一身份只运行一份。Build before stopping services, reject omitted mounts and verify the running images. Backups contain managed volumes and a manifest, not images, the instance `.env` or the host OS. Recovery uses fresh volumes and exact images already on the target daemon. Across daemons the operator must serialize operations and prevent duplicate active identities.
- **模型与补丁性能 / Streaming and patch performance**：三种模型流检查结束事件、取消、损坏数据与重复工具调用；并发访问合并设备活跃时间写入。Host 补丁复用源摘要、流式写输出。[同盘复测](docs/ARCHITECTURE.md#host-patch-measurement)记录冷、热输入页的墙钟和补丁进程 RSS；不作为整机容量数据。All three adapters check completion, cancellation, invalid data and duplicate calls. Concurrent device activity shares a disk write; the patcher reuses source hashes and streams verified outputs. The [same-disk comparison](docs/ARCHITECTURE.en.md#host-patch-measurement) reports wall time and patch-process RSS for cold and warm input pages, not whole-guest capacity.
- **后台记忆 / Background memory**：模型连接在回合结束后的记忆提取中断开时，保留已完成的聊天，记录该次提取失败，不再因无人读取的结果 Promise 退出 Host；其他未处理异常仍按原规则报错。A failed post-turn memory request is reported without terminating the Host or losing the completed reply. Unrelated unhandled errors are not suppressed.
- **客户端与管理页 / Clients and admin**：Windows 安装器按文件归属升级与卸载，可并行迁移无收据旧版。桌面和 Android 修复短流重连及分块上传；Android 生成失败保护旧输出，iOS 从固定清单读取版本。管理页显示真实断线状态，CLI 在发送请求前拒绝无效选项。Windows tracks owned files and supports side-by-side legacy migration. Desktop and Android fix reconnect and upload handling; Android protects existing outputs and iOS reads its version pins from the manifest. Admin status no longer remains ready after disconnect and the CLI rejects invalid flags before making requests.
- **验收与文档 / Verification and documentation**：两次 2C2G 候选诊断均未通过。2C4G、4C8G 分别记录了新装构建、真实模型对话、取消和原设备重启后读回；仅为功能观察，不是容量或前后对照。各包的双语手册区分这些结果与历史验证；没有最低或推荐配置。Both isolated 2C2G candidate diagnostics missed a deadline. Separate 2C4G and 4C8G VMs recorded fresh builds, real-model chat, cancellation and post-restart readback by the original device. These are functional observations, not capacity tests or before/after comparisons. The shared bilingual guides distinguish them from historical tests. There is still no minimum or recommended hardware rating.
- **首页与 CI / Homepage and CI**：首页注明由 6.2Astra 和 Opus5.5 一起维护。Windows 安装器的 GitHub Actions 验收与回归模板一样放在 `ci/`（`ci/installer-native.yml`），默认不运行。The homepage names 6.2Astra and Opus5.5 as maintainers. The Windows installer's GitHub Actions acceptance is an inactive template in `ci/installer-native.yml`, like the regression template.

## 1.0.0（2026-11-10）

**修复**

- **Windows**：
  - Bot 生成的图片和截图在客户端里一直显示加载中；
  - 中文 Windows 上本机命令的输出乱码。
- **联网工具**：
  - 新版 Claude 不接受强制工具调用，导致联网失败；
  - 并行搜索中有一路超出次数时，整次搜索被判失败。

  - 指定画面比例时 OpenAI 图片接口报错；
